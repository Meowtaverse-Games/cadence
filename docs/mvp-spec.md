# Cadence MVP 仕様

## 目的

先に決めた時間割（例: 19:00〜22:00 の間、10分は自由・20分はブロックを繰り返す）に従い、
iPhone、Android、Windows PC の指定アプリを、利用者が何も操作しなくても自動でブロック・解除する。
ポモドーロの「集中」と「休憩」を、本人の意思ではなく時間割で強制する。

## 決定済みの前提

| 項目 | 決定 |
|---|---|
| 利用形態 | 利用者本人が自分の端末に設定する（保護者による管理は MVP の対象外） |
| iOS | Swift / SwiftUI、iOS 16 以上、`FamilyControls` の `.individual` 認可 |
| Windows | C# / .NET 8 のタスクトレイ常駐アプリ（Windows サービスにはしない） |
| Android | Kotlin / Jetpack Compose のホームアプリ（ランチャー）。前面のアプリの検知でブロック画面を出す。ユーザー補助サービスと端末管理（Device Owner）は使わない |
| 同期 | Firebase（Authentication のメール・パスワード、Cloud Firestore）。同期するのは時間割だけ |
| 時間割の編集 | iPhone アプリだけで行う。Windows と Android は読み取り専用 |
| ブロック対象 | 端末ごとに選び、その端末にだけ保存する（同期しない）。iPhone はアプリ選択画面、Windows は exe 名、Android はパッケージ名 |
| タイムゾーン | MVP は `Asia/Tokyo`（UTC+9 固定、夏時間なし）だけを扱う |
| 配布 | iOS は Codemagic でビルドし TestFlight で配布。Windows は GitHub Releases の Setup.exe。Android は Play ストアを通さず、署名した APK を直接入れる |
| 実機確認 | 配布用 entitlement の承認前は、Codemagic で開発用の署名のビルドを作り、登録した端末に入れて確かめる |
| bundle ID | `com.meowtaverse-games.cadence` |

## 時間割のデータ

Firestore の `users/{uid}/config/timetable` の1文書に、時間割全体を保存する。

```json
{
  "schemaVersion": 1,
  "timeZone": "Asia/Tokyo",
  "patterns": [
    {
      "id": "p1",
      "name": "平日の夜",
      "enabled": true,
      "weekdays": [1, 2, 3, 4, 5],
      "start": "19:00",
      "end": "22:00",
      "segments": [
        { "kind": "free", "minutes": 10 },
        { "kind": "block", "minutes": 20 }
      ]
    }
  ],
  "updatedAt": "<server timestamp>"
}
```

- `weekdays` は ISO 8601 の曜日（1 = 月曜 … 7 = 日曜）。窓の `start` が属する日の曜日で判定する。
- `start` と `end` は `timeZone` での時刻（`HH:mm`）。`end < start` は翌日の `end` まで、
  `end == start` は翌日の同じ時刻までの 24 時間を表す。
- `timeZone` は MVP では `Asia/Tokyo` だけを許す。実装は、IANA のタイムゾーンデータベースを
  引かずに UTC+09:00 の固定オフセットで計算してよい（Windows で ICU に依存しないため）。
  将来ほかのゾーンを許すときは、夏時間の扱いを決めてから `schemaVersion` を上げる。
- 時刻の計算は端末のタイムゾーンではなく `timeZone` で行う。iPhone と PC のタイムゾーンの
  設定が違っても、同じ瞬間にブロックが始まるようにするため。
- 分はすべて経過時間で数える（UTC+9 固定なので壁時計と一致する）。
- 上の例の値は合成データである。

### 検証規則

文書は全体として「有効」か「無効」のどちらかになる。一部のパターンだけを使うことはしない。
次のどれかに当たれば無効とする。未知の追加フィールドは無視する。

型の定義（すべてのフィールドに共通）:

- 整数: JSON の数値で、値が整数であるもの。`10.0` は `10` と同じ整数として扱い、`10.5` は整数でない。
  真偽値や文字列は整数ではない。Firestore には integerValue で保存する。
- 真偽値: JSON の `true` / `false` だけ。`0` / `1` は真偽値ではない。
- 文字数: Unicode のコードポイントの数（Swift は `unicodeScalars.count`、C# は
  `EnumerateRunes().Count()`）。
- 文字列の比較: コードポイント列が同じときだけ等しいとする（Unicode の正規化をしない）。`id` の重複、
  `timeZone`、`kind` の判定に使う。Swift の `String ==` と、`String` を要素やキーにする
  `Set` / `Dictionary` は正準等価で比べるので使わず、`unicodeScalars` の列で比べる
  （`"\u00e9"` と `"e\u0301"` は別の `id`）。C# の `StringComparer.Ordinal` と同じ結果になる。
- iOS では Firestore の SDK と `JSONSerialization` が整数・小数・真偽値をどれも `NSNumber` で返すので、
  型の判定には注意する（PR 2 と PR 4b）。

- 文書
  - `schemaVersion` が整数の `1` でない
  - `timeZone` が文字列 `"Asia/Tokyo"` でない
  - `patterns` が配列でない、または 21 件以上ある（0 件は有効で、ブロックが無い状態を表す）
- パターン（有効・無効を問わず全件）
  - `id` が空でない文字列でない、またはほかのパターンの `id` と重複する
  - `name` が 1〜40 文字の文字列でない
  - `enabled` が真偽値でない
  - `weekdays` が空、1〜7 の範囲外の値や整数でない値を含む、または重複を含む
  - `start` か `end` が正規表現 `^([01][0-9]|2[0-3]):[0-5][0-9]$` に一致しない
    （`9:00` と `24:00` は無効）
  - `segments` が空、または 21 件以上ある
  - セグメントの `kind` が `"free"` と `"block"` 以外
  - セグメントの `minutes` が整数でない、または 1〜720 の範囲外
  - `kind: "block"` の `minutes` が 15 未満（iOS の `DeviceActivity` は 15 分未満の区間を監視できないため）
- 有効なパターン（`enabled: true`）だけに課す規則
  - `block` のセグメントが1つも無い
  - ほかの有効なパターンと窓が重なる。窓は半開区間 `[開始, 終了)` として、1週間の
    くり返しの上で比べる（日曜から月曜への折り返しを含む）。終わりと始まりが接するだけ
    （終了 == 開始）は重なりとしない

iPhone は保存の前に検証し、無効なら保存せずに理由を画面に示す。両方の端末は読み込み時にも検証し、
無効な文書は使わずに、直前に有効だった時間割を使い続ける。そのとき Windows はトレイの表示で
「時間割を読み込めません」と知らせる。

### 展開規則（時間割 → ブロック区間）

入力は有効な時間割と期間 `[from, to)`、出力はブロック区間（半開区間 `[start, end)`）の一覧で、
開始時刻の昇順に並べる。区間の時刻は UTC の ISO 8601（秒まで、`Z` 付き。例:
`2026-01-05T10:10:00Z`）で表す。

1. 有効なパターンごとに、`from` の日付（`timeZone` で）の前日から `to` の日付までの各日について、
   曜日が `weekdays` に含まれる日の窓を求める。前日を含めるのは、日をまたぐ窓を拾うためである。
2. 窓の開始から `segments` を順に並べ、窓の終了まで繰り返す。窓の終了を越えるセグメントは
   終了で打ち切る。
3. 同じ窓の中で、終了と開始が一致して隣り合う `block` 区間を1つにまとめる。窓やパターンを
   またいで結合はしない（したがって区間は最長 24 時間）。
4. まとめたあとで 15 分未満の `block` 区間を捨てる（自由時間として扱う）。
5. 期間 `[from, to)` と重なる区間を、期間の境界で切り詰めずにそのまま返す。

例: `block` 25 分だけのパターンを 19:00〜22:00 に置くと、2. で 21:55〜22:00 の 5 分が
できるが、3. で前の区間とまとまるので、結果は 19:00〜22:00 の1区間になる。

この規則は Swift（`ios/CadenceCore`）、C#（`windows/Cadence.Core`）、Kotlin（`android/core`）に
実装する。3つが一致することを、`spec/fixtures/*.json` の共通テストケースで確かめる。
各ケースは、入力の時間割、期間、期待する結果（ブロック区間の一覧、または「無効」）を持つ。
少なくとも次を含める。

- 基本形（自由10分・ブロック20分）、ブロックから始まる形（ブロック25分・自由5分）
- 窓の終わりで切れて 15 分以上残るブロック、15 分未満で捨てられるブロック
- `block` だけのパターン（3. で1区間にまとまる）
- 日をまたぐ窓（23:00〜01:00）と 24 時間の窓、期間の開始が日をまたぐ窓の途中にある場合
- 曜日の境目（日曜から月曜）、期間の境界をまたぐ区間（切り詰めない）
- 検証規則の各項目について、無効になる入力を1つずつ（14 分のブロック、窓の重なり、
  日曜から月曜への折り返しでの重なり、接するだけの窓は有効、空の `weekdays`、`24:00`、
  未知の `kind`、`minutes: 10.5`、`weekdays: [1.5]`、`enabled: 1`、重複した `id`、
  `block` の無い有効なパターンなど）
- 型の定義の境目（`minutes: 10.0` と `schemaVersion: 1.0` は有効、絵文字や結合文字を含む
  40 コードポイントの `name` は有効で 41 コードポイントは無効、正準等価だがコードポイント列が
  違う2つの `id`（`"\u00e9"` と `"e\u0301"`）は重複ではなく有効）

## iOS アプリ

### 構成

- アプリ本体（SwiftUI）
- `DeviceActivityMonitor` extension: 区間の開始と終了で shield をかけ外しし、次の区間を登録する
- `ShieldConfiguration` extension: ブロック画面に「集中の時間です」と解除時刻を表示する
- App Group `group.com.meowtaverse-games.cadence` で、本体と extension が次を共有する:
  検証済みの時間割（JSON）、`FamilyActivitySelection`、最終同期時刻
- 本体と extension は、`CadenceCore` で時間割から区間を展開する。展開済みの区間を保存して
  使い切ることはしない（アプリを開かなくてもブロックが続くようにするため）
- Firebase は本体だけが使う。extension は Firebase を読み込まない（extension の
  メモリ上限が小さいため）。`CadenceCore` は Foundation だけに依存する

### 同期

本体はバンドルに `GoogleService-Info.plist` があるときだけ Firebase を初期化する。
無ければ「このビルドには Firebase の設定がありません。時間割はこの端末にだけ保存されます。」と表示し、
端末だけで編集・ブロックする。設定はあるが未サインインなら
「サインインしていないため、時間割は同期されません。」と表示する。
メール・パスワードでサインインし、状態は FirebaseAuth の Keychain 保存で維持する。
アカウント作成とパスワード再設定の UI は置かない。失敗は日本語で案内する。
サインアウトしても時間割・ブロック対象・監視・shield を変えない。

サインイン中、本体が前面・背面で動作している間は `users/{uid}/config/timetable` の snapshot listener を維持し、
サインアウトで外す。Firestore の永続オフラインキャッシュを使う。BGAppRefreshTask での取得は行わない。
文書の値の木を `TimetableParser.parse(object:)` で検証する。`updatedAt` など未知の値は無視し、
整数の小数表現（10.0）を落とさず、文字列を正規化せずに端末の編集用モデルへ変換する。

「ひも付け済み」は uid ごとに本体の UserDefaults へ保存し、サインアウトで消す（App Group には置かない）。
ひも付け前の判断はサーバー由来（`isFromCache == false`）かつ書き込み保留でない snapshot だけで行う。
キャッシュだけでは選択・採用・アップロード・ひも付けを決めない。

| 状態 | サーバーの文書 | 端末との関係 | 行動 |
|---|---|---|---|
| ひも付け前 | 無い | 有効な端末時間割あり | 端末の内容をアップロードし、completion 成功後にひも付ける |
| ひも付け前 | 無い | 端末時間割なし | 何も書かずにひも付ける |
| ひも付け前 | 有効 | 同じ | ひも付ける。再登録しない |
| ひも付け前 | 有効 | 端末時間割なし | 端末へ保存し、ひも付けて全解除・再登録する |
| ひも付け前 | 有効 | 違う | 両方の要約を表示し、利用者に選ばせる |
| ひも付け前 | 無効 | 任意 | 端末を維持し、検証コードを案内。有効な端末時間割があれば上書きを選べる |
| ひも付け後 | 有効・pendingWrites なし | 違う | 端末へ保存し、全解除・再登録する（キャッシュ由来でも同様） |
| ひも付け後 | 有効・pendingWrites なし | 同じ | 再登録しない |
| ひも付け後 | pendingWrites あり | 任意 | 自分の書き込みの反映なので端末を変えない |
| ひも付け後 | 無い（サーバー由来） | 任意 | 端末を維持し「サーバーに時間割がありません」。次の保存で作成する |
| ひも付け後 | 無効 | 任意 | 端末を維持し「サーバーの時間割を読み込めません（コード）」 |

初回の違いは「この iPhone の時間割をサーバーに上げる」「サーバーの時間割を使う」の2択。
両方のパターン数・各パターンの名前・時間帯・曜日を示す。選ぶまでは端末のブロックを続け、
追加・変更・削除を無効にし、理由を示す。ひも付け前なので再起動後もサーバー確認後に再び選択を表示する。
アップロードを選ぶと書き込みの確定後にひも付ける。サーバーを選ぶと端末への保存成功後にひも付け、再登録する。
無効なサーバー文書には「この iPhone の時間割で上書きする」を提示し、確定後にひも付ける。
初回アップロードの確定待ちも編集を止める（サインアウトは可能）。
初回アップロードが失敗したセッションでは、自動の初回アップロードを抑止し、後続の snapshot でも
失敗の案内と手動の再試行ボタンを維持する。有効なサーバー文書も自動では採用・ひも付けせず、利用者の選択を待つ。
再試行は利用者の操作時だけとし、サインアウト・別 uid への切り替えで抑止を解除する。

編集時は検証、端末保存、内容が変わった場合の全解除・再登録を先に行い、サインイン・ひも付け済みなら
サーバーへも保存する。オフラインでは SDK が書き込みを溜める。書き込みに失敗しても端末の内容は維持し、
「サーバーに保存できませんでした（ドメインとコード）」と表示する。その後の snapshot は上表に従う。
ひも付け後の書き込み拒否を受けてサーバーの時間割を採用した場合は「サーバーに保存できなかったため、サーバーの時間割に戻しました（ドメインとコード）」と案内し、利用者が閉じるか次の保存が成功するまで、snapshot の確認や「同期済みです」で消さない。
書き込みは merge なしの `setData` で、`schemaVersion`、`timeZone`、`patterns`、`updatedAt` の4キーだけ。
整数は Swift の Int、`updatedAt` は毎回 `FieldValue.serverTimestamp()` とする。

内容比較は schemaVersion・timeZone・patterns（配列の順序を含む）だけで行い、updatedAt は除外する。
文字列はコードポイント列で比較する。内容が同じなら起動・前面・再接続でも全解除しない。
サーバー由来の snapshot で端末との一致を確認した時刻（採用時を含む）、または書き込み completion 成功時刻を
App Group の最終同期時刻として保存し、画面に示す。

listener のエラーでは端末時間割とサインイン状態を保ち、日本語とエラーのドメイン・コードを示す。
認証期限切れ・無効トークン・未認証ではサインインが必要と案内する。
`GroupStore.record` の app カテゴリには、snapshot の fromCache/pendingWrites、missing/invalid code/
valid same/valid changed、行動（adopt/upload/askUser/keep/markLinked）、書き込みの成功・失敗を残す。
snapshot の種類と行動の組が直前に記録した snapshot と同じで、行動が keep の場合は重複記録しない。
セッション変更時は比較対象をリセットする。keep 以外の行動、書き込みの成功・失敗、listener エラーは常に記録する。
失敗理由はドメインとコードだけとし、時間割の中身・uid・メールアドレス・パスワードは記録しない。
サインアウト前の listener や書き込みの遅延コールバックで、次のセッションの端末状態を変えない。

### スケジュールの登録

- ブロック区間ごとに、繰り返しのない `DeviceActivitySchedule` を1つ登録する
  （名前は区間の開始時刻から作る）。開始と終了の `DateComponents` は、区間の瞬間を
  登録する時点の `Calendar.current`（端末のタイムゾーン）で年・月・日・時・分に変換して作る。
- 同時に登録するのは、これから始まる区間（ブロック中の区間を含む）の先頭から最大 7 件と、
  見張り用の activity 1 件の計 8 件までとする（OS の同時監視数の上限を避けるため）。
  区間は現在から 14 日先までを展開して選ぶ。
- 見張り用の activity は、毎日くり返す schedule（例: 毎日 00:00〜23:59）とし、そのイベントでも
  判定と登録のやり直しを行う。電源が切れていた間に登録済みの区間をすべて過ぎても、
  利用者の操作なしで連鎖を再開するためである。さらに本体は `BGAppRefreshTask` でも登録をやり直す
  （実行の時刻は OS が決める）。
- shield をかけるか外すかは、イベントの種類で決めず、毎回「時間割と時刻から、その時点が
  ブロック区間の中か」で決める（冪等にする）。判定する時点は、`intervalDidStart` では
  `max(現在時刻, その activity の開始時刻)`、それ以外では現在時刻とする（イベントが開始より
  わずかに早く届いても、区間を取り逃さないため）。extension は `intervalDidStart` と
  `intervalDidEnd` のどちらでもこの判定を行い、shield のかけ外しまでをコールバックの中で済ませて
  すぐに返す。終わった activity の `stopMonitoring` と、件数を保つための次の区間の登録（照合）は、
  コールバックから戻ったあとにプロセス内で順に行う。コールバックの中で `DeviceActivityCenter` を
  同期で呼んでいた版では、1回の処理に数十秒〜数分かかることが実機（iPadOS 26.5）で観察されたためである
  （OS 側がコールバックの完了を待つ間、呼び出しの返事が来ないと見ている）。
- 照合は「今登録されている activity」と「あるべき activity」を比べ、要らないものだけを解除し、
  足りないものだけを登録する。同じなら何もしない。
- extension がブロック対象の選択を読めないとき（ファイルはあるが、読み出しやデコードに失敗したとき。
  再起動後の初回ロック解除前を含む）は、shield も監視も変えずに記録だけを残す。ファイルが無いとき、
  または選択が空のときは、ブロックせず監視も止める。
- extension が時間割を読めないとき（ファイルはあるが、読み出し・デコード・時間割としての検証に
  失敗したとき。再起動後の初回ロック解除前を含む）は、shield も監視も変えずに記録だけを残す。
  照合も行わず、登録の解除・登録・activity の履歴の書き換えをしない。ファイルが無いときは、
  ブロックせず監視も止める。本体で読めないときは、従来どおりファイルが無いときと同じ扱いにする。
- 時間割を保存したとき、ブロック対象の選択を保存したとき、Firestore から変更を受け取ったとき、
  端末のタイムゾーンが変わったとき、利用者が手動で再登録したときは、登録をすべて解除してから
  登録し直す。アプリの起動時、前面に戻ったとき、権限の状態が変わったとき、`BGAppRefreshTask` では、
  すべては解除せず照合だけを行う（全解除は進行中の activity の `intervalDidEnd` と、登録し直しによる
  `intervalDidStart` の連鎖を起こすため）。どの場合も本体からも
  同じ判定で `ManagedSettingsStore` の shield を直接かけ外しする。
- ブロック中の区間は元の開始時刻のまま登録する。

### 実機で確かめること（PR 4a）

次は資料だけでは確かめきれないので、実機で確かめ、違っていればこの節を直す。

- 15 分の下限と、24 時間の区間を登録できること
- 同時監視数の上限
- 開始時刻が過去の区間を登録したとき、すぐに `intervalDidStart` が呼ばれるか
- `stopMonitoring` が `intervalDidEnd` を呼ぶか。呼ぶ場合も、冪等な判定によってブロック中の
  shield が外れたままにならないこと
- 区間の境目（前の区間の終了と次の区間の開始が同時）で shield が外れたままにならないこと
- `intervalDidStart` が区間の開始より早く届くことがあるか
- 電源を切る、または再起動して、登録済みの区間をすべて過ぎたあと、操作なしで次のブロックが
  かかるか（見張り用の activity と `BGAppRefreshTask` で連鎖が再開するか）
- 端末のタイムゾーンを、アプリを開いたまま変えた場合と、アプリを開かないまま変えた場合の
  それぞれで、同じ瞬間にブロックが始まるか
- `DateComponents` に `timeZone`（Asia/Tokyo）を入れた場合に、DeviceActivity がそれを尊重するか。
  尊重するなら、端末のタイムゾーンで変換する方式より堅いので、そちらに切り替える

### 画面

- 同期: 未サインインならメールアドレス・SecureField のパスワード・サインインボタン。
  サインイン中はメールアドレス・同期状態・最終同期時刻・サインアウトボタン。
  サインアウト前に「サインアウトしても、この端末の時間割とブロックはそのまま続きます。」と確認する
- 初回の時間割の選択: 両方の要約と、iPhone の時間割をアップロード／サーバーの時間割を使う選択肢
- Screen Time の権限の取得
- 今の状態（ブロック中か自由時間か、次の切り替え時刻）
- 時間割の一覧と編集: 名前、曜日、開始・終了、セグメント（テンプレート: ブロック25/自由5、
  ブロック50/自由10、自由10/ブロック20、および手入力）。保存時に検証し、エラーを画面に示す
- ブロックするアプリの選択（`FamilyActivityPicker`）

## Windows アプリ

- Setup.exe で入れた版は Velopack で GitHub Releases の安定版を起動約1分後・以後6時間ごとに確認する。
  ダウンロードは裏で行い、ブロック中と次の開始まで5分未満の時間には入れ替えない。
  ちょうど5分前は可。設定画面を閉じるまで待ち、1分ごとに条件を見直して自由時間に再起動する。
  確認・ダウンロード・適用の失敗でもブロックと同期を続け、次の確認時刻に再試行する。
  設定・時間割・サインイン状態は `%APPDATA%\Cadence` に保持する。手動配置版は自動更新しない。

- タスクトレイに常駐する。アイコンのツールチップに、今の状態と次の切り替え時刻を出す。
- サインイン状態を保つ。Firebase Authentication の REST API でサインインし、refresh token を
  DPAPI（CurrentUser）で暗号化して `%APPDATA%\Cadence\` に保存する。
- 60 秒ごとに、Firestore の REST API で時間割の文書を取得する。取得に成功した有効な時間割を
  `%APPDATA%\Cadence\` にキャッシュし、ネットワークが無いときはキャッシュで動き続ける。
  Firestore の typed JSON は普通の JSON に直してから検証する:
  - `integerValue` は文字列（例: `"10"`）で来るので整数にする。`doubleValue` は丸めずに数値のまま渡す。
    `"NaN"` や `"Infinity"` のように文字列で来た値は数値ではないので、型の誤りとして無効になる。
  - 空の配列は `{"arrayValue": {}}`、空のマップは `{"mapValue": {}}` で来る（`values` / `fields` が無い）。
    それぞれ空の配列・空のオブジェクトにする（パターンが0件の時間割を無効と取り違えないため）。
  - `nullValue` は null、`timestampValue`（`updatedAt`）は文字列にする（検証の対象外で無視される）。
- 取得の結果ごとの扱い（ブロックが外れる方向に倒さない）:
  - 文書が無い（404）: キャッシュがあれば使い続け、「サーバーに時間割がありません」と示す。
  - ネットワークの失敗、タイムアウト、5xx、429: キャッシュで動き続け、次の周期で再試行する。
  - 401: ID トークンを refresh token で取り直し、1回だけ再試行する（ID トークンは約1時間で切れるので、
    期限の前にも取り直しておく）。
  - サインインが必要な状態にするのは、取り直し自体が失敗したとき（`INVALID_REFRESH_TOKEN`、
    `TOKEN_EXPIRED`、`USER_DISABLED`、`USER_NOT_FOUND`）だけ。一度だけ通知する。
  - 403（ルールや uid の食い違い）: サインインの状態は変えず、「時間割を読む権限がありません」と示す。
  - どの場合も、キャッシュの時間割でのブロックは続ける（サインアウトしてもブロックは外れない）。
- ブロック中は 2 秒ごとにプロセスを調べ、ブロック対象に一致するプロセスを、子プロセスも含めて終了し、通知を出す
  （同じ exe の通知は1分に1回まで）。終了できなかったプロセス（管理者権限で動くゲームなど）は、
  ログに残して通知で知らせる。
- exe 名の扱い: 保存する名前は拡張子 `.exe` を含む形（例: `steam.exe`）にそろえる。入力に
  `.exe` が無ければ付け、前後の空白を除く。比べるときは `Process.ProcessName` に `.exe` を
  付けた名前と、大文字小文字を区別せずに比べる。
- 設定画面: サインイン、ブロックする exe 名の一覧（実行中のプロセスから選んで追加できる）、
  Windows のログオン時に起動する（`HKCU\...\Run`）のオン・オフ。ブロックする exe 名は
  `%APPDATA%\Cadence\` にだけ保存する。
- Firebase の接続情報（Web API キー、プロジェクト ID）は `%APPDATA%\Cadence\cadence-firebase.json`
  （`{ "apiKey": "...", "projectId": "..." }`）から読む。リポジトリには含めない
  （Firebase CLI の `firebase/firebase.json` とは別物）。
- 時間割もキャッシュも無いときはブロックせず、トレイの表示で知らせる。

## Android アプリ

ホームアプリ（ランチャー）として動き、ブロック中はブロック対象のアプリをホームから隠す。
ホームを通らずに開いた場合（通知、最近使ったアプリ、他のアプリのリンク、検索など）と、ブロックの区間が
始まった時点でブロック対象が前面にあった場合（遊んでいる途中のゲームなど）は、前面のアプリを検知して
ブロック画面を前に出す。Android には iOS の Screen Time にあたる公開 API が無く、ユーザー補助サービス
（AccessibilityService）は Play ストアの審査が厳しく、端末管理（Device Owner）は端末の初期化が要るため、
この2つは使わない。

### 構成

- `android/` に Gradle のプロジェクトを置く。Gradle wrapper をコミットし、依存の版は version catalog
  （`android/gradle/libs.versions.toml`）で固定する。動的な版（`+`、`latest.release`）は使わない。
  - `android/core`: 時間割の検証と展開（Kotlin/JVM、Android に依存しない）。`spec/fixtures/` の
    共通テストケースを JUnit で読む。JSON の値の木を受け取って検証する入口を持つ
    （Firestore の値を直してから渡すため）。
  - `android/app`: アプリ本体（Kotlin、Jetpack Compose）。
- applicationId は `com.meowtaversegames.cadence`（Android の ID にはハイフンを使えないので、
  iOS の bundle ID と違う）。
- minSdk は 29（Android 10。`UsageEvents.Event.ACTIVITY_RESUMED` を使うため）。targetSdk と
  compileSdk は実装の時点の最新の安定版にする。
- 文字数とコードポイント列の比較は、Kotlin でも Swift・C# と同じ定義に従う（`String.length` は
  UTF-16 の長さなので使わず、`codePointCount` やコードポイントの列で数え・比べる）。

### ホーム画面

ミニマルな縦一列のランチャーとする。アイコンの格子は使わない。見た目は Cadence 独自のものとし、
既存のランチャーの名前・アイコン・画面をまねない。

#### 画面の構成

ホームは1本の縦スクロールにする。上から次の順に並べ、別の画面（引き出し）に切り替えない。

1. 上部: 時刻と日付、今の状態（「集中の時間 · 20:30 まで」「自由時間 · 次の集中 20:30」
   「時間割がありません」など）、警告の行、ブロック中の1行。右上に設定の画面を開く歯車のアイコンを置く
   （文字の「設定」は出さない。読み上げの名前は「設定」、タップできる大きさは 48dp 以上）。
2. ウィジェット（0 個以上。「ウィジェット」の節）
3. お気に入り: 利用者が選んだアプリを、アイコンと名前で縦に並べる。数の上限は無い。並べ替えができる。
   「お気に入り」の見出しは出さない。お気に入りが1つも無いときだけ、追加の仕方を1行で示す。
4. すべてのアプリ: 見出しごとに区切り、名前の順に並べる（下の「並び順」）。

- 時刻と日付のタップ: 時刻をタップすると時計のアプリ（`AlarmClock.ACTION_SHOW_ALARMS`）、日付をタップすると
  カレンダーのアプリ（`Intent.CATEGORY_APP_CALENDAR` のメインの画面）を開く。開けるアプリが無いときは、
  そのことを短く示す。ブロック対象のアプリが開いた場合は、ほかの起動と同じくブロック画面になる。
  時刻と日付の長押しは、上部の余白の長押しと同じメニュー（「ウィジェットを追加」）を出す。
- スクロールの動き: スクロールで新しく画面に現れた行（お気に入り、見出し、すべてのアプリ、検索結果）は、
  そのたびに、左下から弧を描くようにすべり込んで元の位置に収まる（約 0.3 秒）。上下どちらへのスクロールでも、
  指でのスクロールでも、はじいた後の惰性のスクロールでも同じにする。一度画面の外に出て戻った行も、またすべり込む。
  上部とウィジェットは動かさない。最初の表示、ホームボタンや索引での移動、検索の入力や消去、
  一覧の作り直し（アプリの追加・削除、ブロックの切り替え）で現れた行は動かさない。
  端末の「アニメーションを削除」（アニメーションの速度が0）が有効なときも動かさない。
  テーマの「スクロールの動き」で切ることもできる。

- 背景: システムの壁紙をそのまま見せる（`android:windowShowWallpaper`、Activity と Compose の背景は透明）。
  壁紙の上に暗い層や半透明の板を敷かない。文字とアイコンは、テーマの「文字の明暗」で決まる色と、
  その反対の色の小さくぼかした影で読めるようにする。ステータスバーとナビゲーションバーも透明にし
  （edge-to-edge）、そのアイコンの明暗を文字の明暗に合わせる。警告の行やメニューなど、壁紙の上で
  まとまりを示す必要がある所だけ、角の丸い小さな板を使ってよい。
- 頭文字の索引: 画面の右端に縦に置き、スクロールの位置によらず常に出す。なぞると、すべてのアプリの
  該当する見出しへ移り、指の近くにその見出しを大きく出す。索引の先頭に「先頭へ」の印を置き、
  なぞると画面の先頭（上部）へ戻る。索引の幅はアプリの行と重ならないように取り、行の右端の余白とする。
- 検索: 画面の下端に、スクロールしても動かない検索欄を置く（ナビゲーションバーの上）。タップすると
  キーボードが開き、入力中は上部・ウィジェット・お気に入りを畳んで、名前が合うアプリだけを並べる。
  キーボードの決定で先頭の結果を開く。空にするか戻る操作で、元の画面に戻る。
- 並び順: 名前の順（日本語の `Collator`）。見出しは `android.icu.text.AlphabeticIndex` の日本語と英語の
  見出しとし、数字や記号で始まる名前は「#」、漢字で始まる名前など読みが取れないものは末尾の「その他」に入れる。
  一覧は見出しの順に並べ、同じ見出しの中を `Collator` の順にする（索引と一覧の位置をずらさないため）。
- アプリの長押し: お気に入りに追加・外す、集中時間に止めるアプリにする・外す、アプリ情報、アンインストール。
  お気に入りとすべてのアプリのどちらの行でも同じメニューを出す。
- ブロック中: ブロック対象のアプリを、お気に入り・すべてのアプリ・検索結果のすべてから隠し、
  「N 個のアプリを 20:30 まで休ませています」と1行で示す。ブロック対象のアプリが提供するウィジェットも隠す
  （外さない。ブロックが終われば元の位置に戻る）。
- ホームボタンを押すと、検索を閉じ、画面の先頭へ戻る（アニメーションなしで、同期的に）。
- アプリの一覧は `LauncherApps` で取り、追加・削除・更新（`LauncherApps.Callback`）で作り直す。
  対象は端末の利用者本人のプロファイルだけとする（仕事用プロファイルは MVP の対象外）。
- 戻る操作: 検索中は検索を閉じる。それ以外では、Cadence が既定のホームアプリのときは消費して何もしない。
  既定のホームアプリでないときは消費しない。
- MVP の対象外: 通知の表示、ドック、フォルダ、アイコンパック、ジェスチャーの設定、ウィジェットの横並びと
  複数のページ、アイコンの形の変更。

#### ウィジェット

上部の下に、ほかのアプリのウィジェット（App Widget）を縦に並べる。

- 追加: ホームの何もない所（上部の余白）の長押しのメニューと、設定画面の「ウィジェットを追加」から、
  Cadence の選択画面を開く。選択画面は `AppWidgetManager.getInstalledProvidersForProfile` で取った
  ウィジェットをアプリごとにまとめ、名前とプレビュー（`loadPreviewImage`、無ければアプリのアイコン）を出す。
  ブロック中は、ブロック対象のアプリのウィジェットを選択画面にも出さない。
- 置き方: 幅は画面の幅から左右の余白と索引の幅を引いたもの。高さは、ウィジェットの既定の高さ
  （`minHeight`、API 31 以上は `targetCellHeight` も参考にする）から始め、長押しのメニューで段階的に
  変えられるようにする（`minResizeHeight` から `maxResizeHeight` の範囲。縦に変えられないウィジェットは変えない）。
  大きさを `AppWidgetHostView.updateAppWidgetSize`（API 31 以上は大きさの一覧）でウィジェットに伝える。
- 上限: 5 個。超える追加はできないことを示す。
- 長押し: ウィジェットのどこを長押ししても Cadence のメニュー（外す、高さを変える、上へ・下へ、
  設定し直す（設定の画面を持つウィジェットだけ））を出す。短いタップやウィジェットの中のスクロールは
  ウィジェットに渡す。ホームの縦スクロールとウィジェットの中のスクロールが競合する場合は、
  ウィジェットの中を優先しない（ホームのスクロールを止めない）。
- 結び付け: `AppWidgetHost`（ホストの ID は固定）で ID を取り、`bindAppWidgetIdIfAllowed` が通らなければ
  `ACTION_APPWIDGET_BIND` で利用者に許可を求める。設定の画面を持つウィジェットは
  `startAppWidgetConfigureActivityForResult` で開き、取り消されたら ID を消して置かない
  （API 31 以上で `WIDGET_FEATURE_CONFIGURATION_OPTIONAL` のものは、設定を飛ばして置いてよい）。
  どの段階で取り消されても、使わない ID を残さない（`deleteAppWidgetId`）。
- 保存: 並び順と高さを端末内に保存する（同期しない）。起動のとき、`AppWidgetHost.getAppWidgetIds` に
  あって保存に無い ID は消す。保存にあって提供元が見つからないものは、一時的な状態（SD カードの取り外し、
  アプリの無効化）がありうるので保存から消さず、表示もしない。保存から消すのは、置き換えでない削除を
  `LauncherApps.Callback.onPackageRemoved` で受けたとき、利用者が外したとき、起動のときに
  `AppWidgetHost.getAppWidgetIds` に無い保存の ID（Cadence が止まっている間に提供元が削除されるなどして、
  システムが消したもの。戻らない）を見つけたときだけにする（取得に失敗したときは消さない）。上限の 5 個は、
  保存のうち今表示できるもの（提供元が見つかるもの。ブロック中に隠したものを含む）で数える。
- 更新: `AppWidgetHost.startListening` を `onStart`、`stopListening` を `onStop` で呼ぶ。
- 読み込めないウィジェット（提供元のエラー）は、その場所に「読み込めません」と出し、ほかのウィジェットと
  ホームの表示を止めない。

#### テーマ

設定画面の「見た目」で次を選べるようにし、選んだらその場でホームに反映する。端末内に保存し、同期しない。

- 文字の明暗: 「壁紙に合わせる」（既定）/「白い文字」/「黒い文字」。「壁紙に合わせる」は
  `WallpaperManager.getWallpaperColors(FLAG_SYSTEM)` の `HINT_SUPPORTS_DARK_TEXT` があれば黒い文字、
  無ければ白い文字にする。壁紙の色が取れないときは白い文字にする。壁紙の変更
  （`OnColorsChangedListener`）に追従する。
- アクセントの色: 「壁紙から」（既定）と、Cadence 独自のプリセット 6 色。「壁紙から」は API 31 以上では
  端末の動的な色（Material You）を、API 29〜30 では `WallpaperColors.primaryColor` を元にし、文字の明暗に
  対して読める明るさに直す。アクセントの色は、状態の行の印、索引のなぞり中の見出し、並べ替え中の項目など、
  小さな強調にだけ使い、本文の文字の色には使わない。
- 文字の大きさと行の間隔: 「小」「中」（既定）「大」。お気に入りとすべてのアプリの文字の大きさと行の高さを
  まとめて変える。端末の文字の大きさの設定（sp）は引き続き効かせる。どの大きさでも、行のタップできる高さは
  48dp 以上にする。
- スクロールの動き: 「左下から」（既定）/「なし」。「画面の構成」のスクロールの動きを切り替える。
- 設定画面とブロック画面は、テーマの対象外とする（端末のライト・ダークに従う、不透明な画面のまま）。

### ブロック

- ブロック対象はパッケージ名の一覧で、端末のアプリ専用の領域にだけ保存する（同期しない）。
  Cadence 自身、既定の電話アプリ、システムの設定アプリは選べない（権限を直せなくなるのを防ぐため）。
- ブロックするかどうかは、イベントの種類で決めず、毎回「時間割と時刻から、その時点がブロック区間の中か」で
  決める（冪等にする）。区間は `android/core` で現在から 14 日先まで展開して求める。

#### 照合

すべてのきっかけで、同じ「照合」を行う。照合は次の3つを順に行う。

1. 今がブロック区間の中かを判定する。
2. 区間の中なら foreground service を始める（動いていればそのまま）。外なら止める。
3. 次の境目（ブロック区間の開始または終了）に、`AlarmManager.setExactAndAllowWhileIdle` でアラームを1件だけ予約する。

きっかけ: 境目のアラーム、端末の起動（`BOOT_COMPLETED`）、アプリの更新（`MY_PACKAGE_REPLACED`）、
時刻とタイムゾーンの変更（`TIME_SET`、`TIMEZONE_CHANGED`）、正確なアラームの権限の変化
（`ACTION_SCHEDULE_EXACT_ALARM_PERMISSION_STATE_CHANGED`）、ホーム画面や Cadence の画面が前面に来たとき、
時間割やブロック対象が変わったとき、service の `onStartCommand`（service は `START_STICKY` とし、
OS に止められて再開したときも照合する）。区間の途中で起動・更新・時刻の変更があっても、その場でブロックを再開する。

Android 12 以降は、アプリが背景にいる間は foreground service を始められない。service を直接始めるのは、
例外として許される入り口（境目のアラームを含む正確なアラームの受信、上のブロードキャストの受信、
Cadence の画面が前面にあるとき）からだけにする。それ以外のきっかけ（Firestore の listener で時間割が
変わったときなど）では、`setExactAndAllowWhileIdle` で現在時刻のアラームを予約し、その受信の中で照合する。
電池の最適化の対象外になっていれば背景からも始められるが、その場合も同じ流れにする。
`ForegroundServiceStartNotAllowedException` は捕まえる（ホームアプリを落とさない）。アラームの受信の外で起きたときは、
ログに残して上の即時のアラームで再試行する。アラームの受信の中で起きたとき（正確なアラームが使えず
`setAndAllowWhileIdle` で代えた場合など）は、即時のアラームはもう予約し直さない（照合の 3. の次の境目の予約は行う）。
ホーム画面の上部と通知に「ブロックを始められませんでした」と示し、次のきっかけで照合する。時間割の変更で始まるブロックには、下の 2 秒の目安は当てはまらない（アラームの遅れを含むため）。

#### 前面のアプリの検知

- ブロック中だけ foreground service（type は `specialUse`、`PROPERTY_SPECIAL_USE_FGS_SUBTYPE` に用途を書く）を動かし、
  通知に「集中の時間です · 20:30 まで」を出し続ける。自由時間は前面のアプリを調べない。
- 画面がついている間は 1 秒ごとに `UsageStatsManager.queryEvents` を読み、前面のアプリを求める。画面が消えている間は
  読むのを止め、`SCREEN_ON` と `USER_PRESENT` で再開し、すぐに1回判定する。service の開始時（区間の始まりを含む）にも
  すぐに1回判定する。
- 前面のアプリ: アクティビティのクラス（パッケージとクラス名の組）ごとに、resumed かどうかの状態を持つ。
  `ACTIVITY_RESUMED` で resumed にし、`ACTIVITY_PAUSED` で外す。`ACTIVITY_STOPPED` は、そのクラスの直前のイベントが
  PAUSED のときだけ外す扱いにし、新しい RESUMED のあとに来た STOPPED は古いインスタンスのものとして無視する
  （同じクラスの画面から同じクラスの画面を開くと `RESUMED → PAUSED → RESUMED → STOPPED` の順に届くため）。
  resumed のクラスを持つパッケージを前面とする（分割画面などで複数あり得る）。
  service の開始時は、端末の起動時刻と現在の 24 時間前の遅い方からさかのぼって読む（区間の前から遊び続けている
  ゲームは、新しいイベントを出さないため）。以後は前回読んだ時刻の 10 秒前から読み、重なったイベントは同じ時刻・
  パッケージ・クラス・種類で除く（時刻が少し戻っても取りこぼさないため）。さかのぼっても前面を決められないときは、
  ブロック画面を出さずにログに残し、次のイベントで判定する。
- 前面のパッケージのどれかがブロック対象なら、ブロック画面を前に出す。Cadence 自身が同時に前面にあっても
  （分割画面など）ブロックする。
- 古い状態の後片付け: `BlockActivity` が全画面で前面に来た（resumed で、`isInMultiWindowMode()` が false）あとで、
  対象のクラスが resumed のまま残っているときは、取りこぼした PAUSED による古い状態とみなして外す（全画面のブロック画面の
  下で対象が本当に resumed であることはないため。ホームに戻ってもブロック画面が出続けるのを防ぐ。上に浮く窓は下の
  「既知の制限」を参照）。`BlockActivity` が
  分割画面の中にいるときは外さない（もう片側で対象が動き続けているため）。そのときは `BlockActivity` が前面にある間は
  起動を繰り返さず、ブロック画面と通知に「分割画面を閉じてください」と示し、分割画面が解かれたら判定し直す。
- この判定（イベント列と `BlockActivity` の状態（resumed か、分割画面の中か）から前面のパッケージと後片付けを求める処理）は
  Android に依存しない純粋な関数として `android/core` か app の中の純粋な Kotlin のクラスに切り出し、合成の入力で
  unit test する。少なくとも、同じクラスから同じクラスを開く、クラッシュで PAUSED が来ない、分割画面（`BlockActivity` が
  全画面の場合と分割画面の中の場合）、ピクチャー・イン・ピクチャー、24 時間の境目の前の RESUMED と後の PAUSED だけが
  ある列、を含める。
- 目安: ブロック対象が前面に来てから、または区間が始まってから 2 秒以内にブロック画面が出る。
  他のアプリのプロセスは終了しない（Android では他のアプリを強制終了できない）。
- ブロック画面を出したのに 3 秒以内に `BlockActivity` が前面に来なかったときは、背景からの画面の起動が止められた
  とみなす（拒まれても例外は来ないため）。ログに残し、ホーム画面の上部と service の通知に
  「ブロック画面を出せませんでした」と、確かめる設定（下の「権限」）を示す。対象が前面のあいだは、1 秒ごとの判定の
  たびに起動を試み続ける。警告は状態として1つだけ示し（試すたびに増やさない）、`BlockActivity` が前面に来たら消す。
- 次は MVP の対象外とする: 別の利用者として動くアプリ（デュアルアプリやクローン、プライベートスペース、
  仕事用プロファイル。`queryEvents` に出ないため）と、ピクチャー・イン・ピクチャーで pause された窓。
- 既知の制限: 全画面の上に浮く窓（端末メーカーのポップアップ表示、freeform、デスクトップ形式の窓）でブロック対象が
  resumed のまま動いている場合、`BlockActivity` が全画面で開く（`isInMultiWindowMode()` が false）と後片付けが働き、
  対象が前面の判定から外れることがある。対象の次のイベントで `BlockActivity` を出し直すが、浮く窓が上に残る場合は
  止められない。`BlockActivity` 自身が窓として開いた（`isInMultiWindowMode()` が true）場合は、分割画面の規則に従う。
  MVP では対応せず、実機で確かめてから扱いを決める。

#### ブロック画面

- `BlockActivity` は全画面で「集中の時間です」と終わりの時刻、「ホームへ」のボタンを示す。戻る操作もホームへ移る。
- ホームのタスクと分けるため専用の `taskAffinity` を持ち、`launchMode` は `singleTask`、最近使ったアプリの一覧に
  残さない（`excludeFromRecents`）。
- 前面に来たら audio focus（`AUDIOFOCUS_GAIN`）を取り、下のアプリの音を止めさせる。ホームへ移るときに手放す。
- アプリの上に重ねる窓（`TYPE_APPLICATION_OVERLAY`）は使わない。重ねるだけでは下のアプリが前面のまま
  動き続け、ゲームの音も止まらないため。画面として前に出し、下のアプリを一時停止の状態にする。

#### 権限

- ブロックに欠かせないもの（欠けていればホーム画面の上部に、何が足りないかと設定画面へのボタンを示す。
  ブロックが効かない状態を黙っていない）:
  - 使用状況へのアクセス（`PACKAGE_USAGE_STATS`）
  - 他のアプリの上に重ねて表示（`SYSTEM_ALERT_WINDOW`。背景から画面を前に出す制限の例外にあたるため）
  - 既定のホームアプリ
  - 電池の最適化の対象外（`REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` で依頼する。端末の電池の管理で
    service やアラームが止められるのを防ぐため）
  - 正確なアラーム: API 33 以上は `USE_EXACT_ALARM`（自動で付与され、利用者が取り消せない。Play ストアの
    ポリシーの制約は直接入れる配布には関係しない）、API 31・32 は `SCHEDULE_EXACT_ALARM`（`maxSdkVersion="32"`）。
    判定は API 31 以上で `canScheduleExactAlarms()`、それ未満は常に可とする。使えないときは
    `setAndAllowWhileIdle` で代え、境目が遅れうることを示す。
- 通知（`POST_NOTIFICATIONS`）が無くても service は動きブロックも効くので、ホーム画面には「通知が出ません」と
  別の表示にする。
- ブロック中に使用状況へのアクセスが取り消されたときは、service を止めずに通知で警告し続け、権限が戻ったら再開する。
- 直接入れた APK では、Android 13 以降の「制限付き設定」で一部の許可を付けられないことがある。設定画面に、
  アプリ情報のメニューから「制限付き設定を許可」する手順と、端末メーカー独自の権限（背景からの画面の表示など）を
  確かめる案内を置く。
- manifest に宣言するもの: `FOREGROUND_SERVICE`、`FOREGROUND_SERVICE_SPECIAL_USE`、`RECEIVE_BOOT_COMPLETED`、
  上の権限、パッケージの可視性のための `<queries>`（`MAIN` / `LAUNCHER` の intent）。

#### 端末内の保存

- ブロック対象、キャッシュの時間割、お気に入りは、アプリ専用の領域にだけ保存する。
- ファイルが無いとき: 時間割が無いならブロックせず、ホーム画面の上部でそのことを示す。ブロック対象が無いなら、
  ブロックするアプリが無い状態として扱う。
- ファイルはあるが読み出し・デコード・検証に失敗したとき: 無いとはみなさない（ブロックが外れる方向に倒さない）。
  プロセスの中に直前の値があれば使い続け、無ければ service と予約を変えずにログに残し、ホーム画面に
  「設定を読み込めません」と示して、次のきっかけで読み直す。
- ログ（ブロック画面を出した時刻とパッケージ、出せなかったこと、照合、予約、権限の状態）は端末の中にだけ残し、
  時間割の中身・uid・メールアドレス・パスワードは残さない。

### 同期

- Firebase の Android SDK（Authentication、Firestore）を使う。`google-services.json` はリポジトリに
  含めない。`android/app/google-services.json` があるときだけ google-services の Gradle plugin を適用する。
  ファイルが無い debug のビルドは、Firebase を初期化せず「このビルドには Firebase の設定がありません」と示して動く
  （CI はファイルなしで debug のタスクだけを動かし、release のタスクは動かさない）。release のビルドはファイルが無ければ
  失敗させる（PR A4）。
- メール・パスワードでサインインする。アカウント作成とパスワード再設定の UI は置かない。失敗は日本語で案内する。
- サインイン中は、アプリのプロセスが動いている間 `users/{uid}/config/timetable` の snapshot listener を保ち、
  サインアウトで外す。ホームアプリなので、プロセスは通常いつも動いている。永続オフラインキャッシュを使う。
- Firestore の値を JSON の値の木に直してから `android/core` で検証する。`Long` は整数、`Double` は
  数値のまま渡す（`10.0` が整数として通るかは検証規則に任せる）。`NaN` と無限大の `Double` は数値ではない値にする。
  `Timestamp`（`updatedAt`）は文字列にする。`GeoPoint`、`DocumentReference`、`Blob` などそのほかの型は
  「対応しない値」にする。どれも、未知のフィールドにあれば無視され、型を検証する位置にあれば文書が無効になる
  （変換で落ちない）。
- 有効な時間割はアプリ専用の領域にキャッシュする。文書が無い・無効・エラーのときは、直前に有効だった時間割で
  ブロックを続け、理由をホーム画面と設定画面に示す（Windows と同じく、ブロックが外れる方向に倒さない）。
  サインアウトしても、キャッシュの時間割でブロックを続ける。
- Android からは書き込まない。

### 設定画面

サインイン、同期の状態と最終同期時刻、権限の状態と各設定画面への移動（既定のホームアプリ、電池の最適化、
制限付き設定と端末メーカー独自の権限の案内を含む）、ブロック対象の一覧（追加・削除）、見た目（「テーマ」の節）、
ウィジェットを追加、版の表示。

debug ビルドだけ、Firebase なしでブロックを確かめるため「今から 15 分ブロックする時間割を入れる」を置く
（合成の時間割を端末のキャッシュに入れる）。release ビルドには含めない。

### 実機で確かめること

- ホームを通らない入り口（通知、最近使ったアプリ、他のアプリのリンク、Google の検索、設定のアプリ情報）から
  ブロック対象を開いたとき、2 秒以内にブロック画面が出ること
- ゲームを遊んでいる途中に区間が始まると、ブロック画面が出てゲームが一時停止し、音が止まること
  （区間の始まりの 10 分以上前から同じゲームを遊び続けている場合を含む）
- 分割画面の片側でブロック対象を開いたとき、ブロック画面が出て、ゲームが動き続けないこと（ブロック画面がもう片側に
  入って対象が動き続ける場合は、「分割画面を閉じてください」が出て、ブロックが外れたままにならないこと）
- 画面を消して置いておいた（Doze）あとでも、区間の始まりにブロックが始まること
- 再起動のあと、操作なしで次の区間にブロックがかかること。区間の途中での再起動とアプリの更新のあとも、
  その場でブロックが再開すること
- 他のアプリが前面にある間に iPhone で時間割を変えて今がブロック区間になったとき、Cadence が落ちずにブロックが始まること
- 端末メーカー独自の電池の管理で service やアラームが止められないこと
- ブラウザやファイルマネージャーから入れた APK で、必要な権限をすべて付けられること（制限付き設定）と、
  背景からの画面の起動が止められたときに「ブロック画面を出せませんでした」が出ること
- 浮く窓（端末メーカーのポップアップ表示、freeform）でブロック対象を開いたときの挙動（「既知の制限」の扱いを決めるため）
- 明るい壁紙と暗い壁紙のそれぞれで、「壁紙に合わせる」の文字が読めること。壁紙を変えたときに追従すること
- ウィジェット: 時計・天気・カレンダーなどを置けること、設定の画面を持つウィジェットを置けること、
  許可を求める画面や設定の画面を取り消しても空の枠や ID が残らないこと、再起動とアプリの更新のあとも残ること、
  ブロック対象のアプリのウィジェットがブロック中に隠れて終わると戻ること、中でスクロールするウィジェット
  （カレンダーの一覧など）があってもホームを縦にスクロールできること

## Firebase

- Authentication: メール・パスワードだけを有効にし、利用者のアカウントを1件だけ手動で作る。
  第三者が新しいアカウントを作れないよう、サインアップを無効にする
  （Identity Platform へのアップグレードが要るかは要確認）。
- Firestore のルール（`firebase/firestore.rules`）: サインインした本人が、自分の
  `users/{uid}/config/timetable` の1文書だけを読み（get）、作成・更新できる。削除と一覧は
  できない。それ以外はすべて拒否する。書き込みでは、書き込み後の文書の形を最小限だけ確かめる:
  キーは `schemaVersion`、`timeZone`、`patterns`、`updatedAt` の4つちょうど（ほかのキーは禁止、
  4つとも必須）、`schemaVersion == 1`、`timeZone == 'Asia/Tokyo'`、`patterns` は 20 件以下のリスト、
  `updatedAt == request.time`。パターンの中身はアプリが検証する。このため iPhone（PR 4b）は、
  書き込みのたびに（一部のフィールドだけを更新する場合も）`updatedAt` を
  `FieldValue.serverTimestamp()` で入れる。入れないと書き込みが拒否される。
  ルールはエミュレーターで自動テストする（`firebase/test/`、CI は `.github/workflows/firebase.yml`）。
- リージョンは `asia-northeast1`。
- 準備の手順（プロジェクトの作成、メール・パスワードの有効化、アカウントの作成、
  サインアップの無効化、ルールのデプロイ、各端末への接続情報の配置）は、PR 3a で
  `docs/firebase-setup.md` に書く。プロジェクトの作成とアカウントの作成は人が行い、
  ルールのデプロイは人の承認を得てから行う。

## 配布

- iOS: Codemagic の `ios-release` ワークフローで App Store 配布の署名を行い、
  App Store Connect にアップロードして TestFlight の内部テストで配る。
  Family Controls の配布用 entitlement が Apple に承認されるまで、TestFlight には出せない。
  Apple の文書（Requesting the Family Controls entitlement）のとおり、Screen Time の extension にも
  同じ申請が要るので、アプリ本体と2つの extension の3つの bundle ID で申請する。
- iOS の SDK の版: Firebase の SDK は XcodeGen の `project.yml` で `exactVersion` を指定して固定する。
  生成した Xcode プロジェクトはコミットしないので、`ios/Package.resolved` をコミットし、
  `ios/scripts/generate-project.sh` がプロジェクトの生成後にそれを
  `ios/Cadence.xcodeproj/project.xcworkspace/xcshareddata/swiftpm/Package.resolved` にコピーする
  （`ios/Package.resolved` が無ければコピーを飛ばす）。CI と Codemagic のビルドは
  `-onlyUsePackageVersionsFromResolvedFile` を付け、`Package.resolved` に無い版を取りに行かない。
  依存を足したり上げたりするときは、Mac または CI の不足時解決で作った `Package.resolved` を `ios/` に戻してコミットする。
  CI はファイルが無い場合だけ解決し、artifact をアップロード後、lock が無いことを明示して失敗する。
  通常の最終 head は lock 付きで成功させる（手順は `ios/README.md`）。
- `GoogleService-Info.plist` はリポジトリに無いので、`project.yml` では `optional: true` を付けて
  参照するか、CI ではダミーを置く。ファイルが無くてもプロジェクトの生成と CI のビルドが通るようにする。
- 実機確認用: Codemagic に開発用の署名のワークフローを置き、登録した端末向けのビルドを作って入れる
  （PR 4a。Family Controls の開発用 entitlement は承認なしで使える）。Codemagic で作った `.ipa` は、
  iPhone をつないだ Mac の Xcode（Devices and Simulators）か Apple Configurator で入れる。
- Windows: 本人の承認後に `windows-vX.Y.Z` タグを push したときだけ、GitHub Actions で
  self-contained のアプリを Velopack で梱包し、GitHub Releases に公開する。main のマージでは公開しない。
  PR / push の CI では公開しない確認用 Setup.exe と更新パッケージを成果物として保存する。
- Android: PR / push の CI（`ubuntu-latest`）で debug の APK を成果物として保存する。debug の APK は、
  secret `ANDROID_DEBUG_KEYSTORE_BASE64` の固定の鍵で署名し、版を上げてもアンインストールせずに上書きで
  入れられる（アンインストールすると端末内の保存が消えるため）。secret が無い実行（fork からの PR など）では、
  その場で作った鍵で署名する。release の署名の鍵も、リポジトリに含めず、CI の secret に置く。GitHub Releases は Windows の自動更新専用なので使わない
  （Velopack は新しい順に 10 件の Release しか見ないため）。配り方と更新の方法は PR A4 で決める。

## MVP の対象外

- 集中時間の記録、カレンダー、ヒートマップ
- iOS の Live Activity とウィジェット
- 解除のしにくさの強化（待ち時間、アプリ削除の防止、Windows サービス化）
- 保護者による管理（`.child` 認可）
- Windows と Android からの時間割の編集、Mac 版
- Android の Play ストアでの配布、ユーザー補助サービスや端末管理によるブロック、別の利用者として動くアプリと
  ピクチャー・イン・ピクチャーのブロック、上に浮く窓のブロック（「前面のアプリの検知」の既知の制限）
- `Asia/Tokyo` 以外のタイムゾーン

| 3b | Windows のトレイアプリ（同期、ブロック、設定画面） | 1 |
| 4a | iOS の Screen Time 連携（extension、スケジュール、shield、画面、端末内だけの時間割の編集）と、Codemagic の開発用署名のワークフロー、`docs/apple-setup.md` | 2 |
| 4b | iOS の Firebase 連携（サインイン、時間割の読み書きと変更の受信、`Package.resolved`） | 4a、3a のルールと Firebase の準備 |
| 5 | Codemagic の設定と TestFlight 配布 | 4b、entitlement の承認 |

| A2b | Android のホーム画面（お気に入り、すべてのアプリの引き出しと索引・検索、ブロック中に隠すこと、長押しのメニュー、壁紙、上部の時刻と状態など）。A2a と A3 で仮のホーム画面に出した状態と警告の表示を引き継ぐ | A2a |
| A2c | Android のホーム画面の作り直し（「画面の構成」の1本の縦スクロール、常に出る索引、下端の検索、壁紙をそのまま見せること）と「テーマ」。ウィジェットの場所は空けておくだけでよい | A2b |
| A2d | Android のウィジェット（「ウィジェット」の節のすべてと、設定画面の「ウィジェットを追加」） | A2c |
| A2e | Android のホームの手直し（時刻と日付のタップ、設定のアイコン、お気に入りの上限をなくし見出しを外すこと、スクロールの動きとテーマの「スクロールの動き」） | A2d |
| A3 | Android の Firebase 連携（サインイン、時間割の受信とキャッシュ）と、`docs/firebase-setup.md` への Android アプリの登録（package `com.meowtaversegames.cadence`）と `google-services.json` の置き場所の追記 | A2a、3a のルールと Firebase の準備 |
| A4 | Android の release の署名と配布の方法 | A2b、A3 |

A2b と A3 はどちらも A2a だけに依存するので、並行して進めてよい。

A4 で決めること: 配り方と更新の方法、Android の開発者確認（developer verification）が直接入れる配布に及ぶ範囲と
その対応（限定配布用のアカウントや adb で入れる方法を含む）。`google-services.json` を含む release の APK は、
公開リポジトリの CI の成果物に置かない。release のビルドは `google-services.json` が無ければ失敗させる。

PR 4 は、Firebase が無くても iPhone でブロックを確かめられるように 4a と 4b に分ける。
4a では時間割を端末の App Group にだけ保存し、4b で Firestore と同期する。

PR 2、3a、3b の実装は互いに依存しないので並行して進める。ただし、PR 3b を実際の Firebase と
Windows で通して確かめるのは、PR 3a の手順で Firebase を準備し、ルールをデプロイしたあとになる。
